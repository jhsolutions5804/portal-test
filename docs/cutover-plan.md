# 본섭 일괄 패치 준비 문서 (테섭 → 본섭)

작성 기준: 테섭 build **20261012w** (커밋 7299ea8 이후). 방침(대표님 확정): **테섭 구축을 끝낸 뒤, 코드 전부 + 현재 본섭에 저장된 데이터를 합쳐 본섭에 한 번에 패치한다.**
이 문서는 그때 쓸 반영 순서·데이터 이전·제거 대상·확인 목록이다. 이식이 진행될 때마다 이 파일을 갱신한다.

## 0. 큰 그림

- 테섭과 본섭은 **별도 Firebase 프로젝트**다(테섭 `portal-test-…`, 본섭 `p4ph2-fab-506a7` 계열). 새 코드는 구포털과 **같은 컬렉션 이름·필드**를 쓰므로, 본섭에 새 코드를 올리면 본섭의 기존 데이터를 그대로 읽는다(데이터를 옮겨 담을 필요가 없는 것이 원칙).
- 테섭에서만 만들어진 데이터(재무회계 장부 입력분, 총무 입력분, 시험용 근로자·계약서 등)는 **본섭으로 복사하지 않는 것이 기본**이다. 필요한 것만 §3의 방법으로 본섭에서 다시 넣는다.
- 본섭 패치는 **복구 지점을 만든 뒤** 한다(§5).

## 1. 반영 순서 (본섭)

1. **복구 지점**: Firestore 내보내기(전체) + 보안 규칙 파일 백업 + 코드 저장소 태그(`prod-before-cutover`) + 서버 함수 현재 버전 기록. (§5)
2. **서버 함수 재배포**: `edoc-functions-ledger_20261011h.zip` (저장소 `portal-functions` 2a65615 이후). 내용: 운행일지(`drive`) 문서는 결재 없이 즉시 확정, 월간 수지 `saveMonthlyPlan`. 
   `firebase deploy --only functions:edoc --project <본섭 프로젝트>` (테섭에서는 `--project test` 로 같은 절차를 이미 쓴다).
3. **보안 규칙 반영**(`firestore.rules`, 테섭·본섭 모두):
   - `isEdocCollection()` 목록에 `'edoc_drive'` 추가
   - `isAdminOnlyCollection()` 목록에 `'general_leases'`, `'general_vehicles'`, `'general_assets'`, `'general_renewals'`, `'general_drive_history'` 추가 (추가 전에는 직원 누구나 읽을 수 있으므로 **총무 데이터를 넣기 전에** 반영)
   - 인사 새 화면이 쓰는 컬렉션은 모두 구포털이 이미 쓰던 것이라 별도 규칙 추가는 없다(§2 표). 단 `hr_calendar_access/config` 의 이메일 목록은 **본섭 값 그대로** 유지.
4. **코드 반영**: 테섭 저장소(`jhsolutions5804/portal-test`) 최종 빌드를 본섭 저장소에 반영. 반영 전 `app/core/config.js` 등 **환경 설정이 본섭 Firebase 를 가리키는지** 확인(테섭 설정이 섞여 올라가지 않게). 빌드 번호·`version.json` 확인.
5. **데이터 후처리**(§3) → **QC**(§6) → 구포털 제거 대상 정리(§4).
6. 문제가 있으면 §5 절차로 되돌린다.

## 4. 구포털에서 제거할 대상 (이식 완료 후)

- 구포털 인사 화면(`hr/index.html`)의 **"근로시간"(초과근로) 탭** — 새 "초과근로 현황 + 출퇴근 달력"과 겹침(자동연동 중복 위험). **가장 먼저 막을 것.**
- 새 화면으로 대체된 탭: 근로자 명부, 연차 현황(등록·수정·사용촉진 제외), 인사 변동, 공고 관리, 채용 지원자, 연봉 제안서, 근로자 면담, 휴직/퇴직 원서, 퇴직금 정산, 해고예고통지서, 인사 캘린더, 인사평가, 급여테이블, 급여명세서, 연봉계약서, 근로계약서.
- **원격 서명 링크·QR·본인 열람 링크·메일 발송**(연봉 제안서·급여명세서·연봉계약서·근로계약서)은 **새 화면으로 이식 완료**(`hr/sign.js`·`hr/sign-io.js`). 서명 페이지 `sign.html` 은 별도 공개 페이지로 그대로 쓴다(§9-1).
- **연차 등록·수정·삭제, 연차사용촉진도 이식 완료** → **구포털 인사(`hr/index.html`)의 모든 기능이 새 화면으로 옮겨졌다.** 본섭 반영 후 QC 가 끝나면 구포털 hr 를 통째로 걷어낼 수 있다(단 `sign.html`·`sign_links` 규칙은 유지).

## 5. 복구(롤백) 절차

1. **패치 전**: `gcloud firestore export gs://<버킷>/pre-cutover-YYYYMMDD` (전체), 보안 규칙 파일을 `backup/` 에 날짜 붙여 보관, 저장소 태그 `prod-before-cutover`, 서버 함수 현재 배포 버전 기록.
2. **코드만 문제**: 저장소를 태그로 되돌려 재배포(데이터 구조는 구포털과 호환이므로 데이터 복구 불필요).
3. **규칙 문제**: 백업한 규칙 파일을 다시 배포.
4. **함수 문제**: 이전 zip 으로 재배포.
5. **데이터 오염(예: 자동연동 중복)**: §3-3 의 `overtime` 중 `edoc_` 로 시작하는 문서만 선별 삭제 후 `edoc_overtime.linkedToOvertime` 을 되돌려 다시 연동 가능. 필요 시 내보내기본에서 컬렉션만 복원.

## 9. 원격 서명·메일 발송 — 반영 시 주의

1. **`sign.html` 은 환경별 Firebase 설정이 들어 있는 파일**이다(테섭 저장소의 것은 테섭 프로젝트를 가리킨다). **본섭 저장소의 `sign.html` 을 유지하고 테섭 것으로 덮어쓰지 않는다.** 새 화면은 자신이 올라가 있는 곳의 `sign.html`(상대 경로)로 링크를 만들므로 코드 자체는 환경 설정이 필요 없다.
2. `sign_links`(+하위 `secure/payload`·`secure/result`)와 `doc_send_log` 의 **보안 규칙은 구포털이 이미 쓰던 것**이다. 본섭 규칙에 그대로 있는지만 확인한다(없던 규칙은 추가하지 않았다).
3. 서명 결과 반영(`syncSignedLinks`)은 이제 **새 연봉·근로계약서 화면을 열 때** 돈다. 구포털 계약서 탭도 같은 일을 하므로 두 화면을 동시에 처음 여는 일은 피한다(이미 반영된 건은 `synced` 표시로 다시 반영되지 않음).
4. 메일 발송은 EmailJS(서비스·템플릿·공개 키는 구포털과 같은 값)이며, 브라우저에서 SDK 를 CDN 으로 불러온다.
5. 링크 생성에는 받는 분의 **휴대폰 번호**(근로자 명부 또는 채용 지원서)가 필요하다(문자 인증용). 번호가 없으면 안내 후 중단된다.

## 10. 보안 메모

- 이 프로젝트 파일에 **GitHub 토큰·서비스 계정 키·클라이언트 암호가 평문으로** 들어 있다. 본섭 패치와 이식이 모두 끝난 뒤 **전부 새로 발급(교체)** 하고 프로젝트 파일에서 지우는 것을 권장한다. 테섭 구축 중 공개된 적이 있다면 즉시 교체.
- 저장소에는 비밀 값 점검(`scripts/secret_check.py`)이 있어 커밋 전에 걸러진다.
