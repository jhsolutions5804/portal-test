# 영업기획 모듈 설계서 (이식 + 신규) — 2026-10-13

구포털 기획(gihoek, 2,468줄 단일 파일)을 새 플랫폼 모듈로 옮기고, 영업·기획 업무 구분과 신규 기능을 얹는다. 인사총무 이식과 같은 방식(공용 사이드바·점검 도구·동결 서식).

## 1. 본섭 업무 흐름 (데이터로 확인, 읽기 전용 조회)
- 프로젝트 8개(전부 진행 중) ↔ PJT 관리 현장 **1:1 연결** — 프로젝트 저장 시 PJT 관리(`pjt_registry`)에 같은 이름의 경량 PJT를 **자동 생성**(기본값), 기본정보 6항목(PJT 코드·내용·현장명·발주처·시공사·협력사)은 양방향 반영.
- 견적 16건: 모두 프로젝트 소속, 발행처 이엔지 13·솔루션 3, 수신처 다람이엔지·귀뚜라미범양냉방, 리비전 최대 r9(번호 `EST-연도-nnn-rN`).

- 거래처 5개. **역할은 "발행처(우리 발행 주체)"와 "수신처(거래 상대)"** — 에스제이는 지급예정서의 수신처라 수신처로 등록된 것이 맞다(오류 아님).

- 대표님 확인: 지금은 이엔지가 견적·청구를 내고 솔루션이 시공·에스제이에 지급하지만, **앞으로는 이엔지 없이 솔루션만**. 협력사는 현재 에스제이만, 늘어날 수 있음.

## 2. 영업 / 기획 구분 (기준: 상대방·돈의 방향·시점, 경계는 수주 시점)

## 3. 구조
- **영업기획 한 모듈, 공용 사이드바**(인사총무와 같은 방식). 권한은 지금과 같이 관리자.
- 사이드바: 홈 / 프로젝트 / 영업(거래처·견적·정산) / 기획(협력사·…) / 이관 예정(회계).
- 정산은 이식 단계에서는 한 화면, 이후 청구(영업)·지급(기획)으로 분리하고 **월말 마감 보기** 추가.
- 이식하지 않은 탭은 옛 화면이 그대로 열린다(인사 때와 같은 방식, 새 화면만 쓰는 동안 옛 화면은 불러오지 않음).

## 4. 설계 원칙
- 컬렉션·필드는 구포털 그대로(`gihoek_*`, `pjt_registry`, `team_rates`, `worker_manday`…) — 본섭 데이터를 옮기지 않고 읽는다.
- **발행처는 설정으로 관리하는 목록**: 이엔지 전용으로 박지 않는다(이엔지 종료 시 기본 발행처만 솔루션으로). 과거 문서는 그대로 보존.
- 견적·정산서 인쇄 서식과 번호 규칙(`EST-…-rN`, `yymmnnn`)은 동결(원본 대조 시험).
- 프로젝트 저장 → PJT 관리 자동 생성·양방향 반영을 저장 동작 점검에 포함.
- 테섭 파일이 기준(본섭 사본과 환경 설정 6줄만 다름 확인).

## 5. 단계
0) 기반(모듈 틀·사이드바·거래처) → 1) 프로젝트 → 2) 견적(리비전 비교, 서식 동결) → 3) 정산(서식·계산 원본 대조) → 4) 홈 → 5) 협력사·위탁 계약·월말 마감(신규) → 6) 회계 이관(비용장부→재무회계) 및 프로젝트 손익.

## 6. 미정
- 위탁 계약서 양식(협력사별 단가, 하도급 법정 서면 요건 — 법무 확인), 청구·지급 분리 시점, 비용장부 이관 방식(전표로 이전 추천).

## 회계 이관 결정 (2026-10-13)
구포털 기획의 회계 탭(비용장부·손익)은 재무회계(재무회계 모듈)가 대체한다. 테섭 실데이터로 확인한 사실:
- 비용장부 235건 중 **170건은 같은 날짜·금액의 전표가 이미 있다**(카드·통장 가져오기로 들어옴). 23건은 같은 날 같은 금액 전표가 이미 다른 건과 짝지어져 **중복 의심**, 42건이 전표에 없음(외상거래 22·급여 4 포함, 외상거래는 매입 세금계산서로 들어왔을 가능성이 크고 급여는 급여명세서 가져오기로 들어옴).
- 따라서 **통째로 옮기면 이중 계상**이 된다 → "비용장부 대조" 화면(영업기획 > 이관 예정)으로 건마다 대조하고, 전표에 없는 건만 재무회계 가져오기 JSON 으로 내려받아 대표님이 확인 후 가져온다(모두 "검토 필요" 표시, 외상거래·중복 의심·급여는 기본 제외).
- **전표 줄에 프로젝트 표시가 아직 없다**(4,578줄 중 0). 비용장부의 프로젝트 표시(91건)는 "프로젝트 표시 대조표(CSV)"로 보존한다 — 재무회계가 전표에 프로젝트 표시를 지원하면 이어받는다. 그 전까지 프로젝트 손익은 청구−지급(공급가액) 기준(프로젝트 화면·월말 마감)으로 본다.
- 본섭 전환 때: 본섭에서도 재무회계 초기 데이터(전표)를 올린 뒤 이 화면으로 대조·가져오기를 한 번 실행하고, 끝나면 이 메뉴와 구포털 기획 화면(gihoek/index.html)을 제거한다.

## 협력사 위탁(하도급) 계약서 (2026-10-13)
- **위치**: 영업기획 > 기획 > 위탁 계약서. 구포털 기획에는 없던 신규 기능(대표님이 "하도급사 공사 위탁 계약서 작성"을 영업·기획 중 어디에 둘지 물으셨고 기획 구역에 둠).
- **저장**: 협력사 문서(`gihoek_companies/<협력사>`)의 `contracts` 배열. 새 컬렉션을 만들지 않아 **보안 규칙 변경이 필요 없다**(거래처 저장은 merge 라 계약서 필드가 지워지지 않는다). 협력사 문서를 삭제하면 그 협력사의 계약서도 함께 사라진다.
- **흐름**: 작성(작성 중, 법정 사항이 비어도 저장) → 인쇄해 양쪽 서명·날인 → 서명일·서면 발급일 기록(서면 발급, 이후 수정 불가) → 내용이 바뀌면 변경 계약서(원 계약은 그대로, parentId 로 연결) → 폐기(기록 유지). 번호는 yymm + 세 자리(전 협력사 통틀어).
- **법정 기재사항 점검표**(`plan/contracts.js`, 「하도급거래 공정화에 관한 법률」 제3조·같은 법 시행령 제3조 2026-08-04 개정판을 2026-10-13 확인): 위탁일·목적물등의 내용, 납품·인도·제공 시기와 장소, 검사 방법·시기, 하도급대금(선급금·기성금 포함)과 지급방법·지급기일, 원재료 등 제공 시 내용, 하도급대금 연동 사항(기간 90일 이내 또는 1억원 이하는 해당 없음으로 보되 법무 확인), **양쪽 서명 또는 기명날인**(한쪽이라도 없으면 서면 미발급), **착공 전 발급**(건설위탁), 서류 보존. 누락이 있으면 서면 발급 기록을 막고, 착공 후 발급은 막지 않되 며칠 늦었는지 경고한다.
- **법무 확인이 필요한 것(대표님 결정·확인 필요)**: ① 이 거래(솔루션 → 에스제이)가 하도급법·건설산업기본법의 적용 대상인지 — 업종(건설업 vs 용역, 세무사 상담 대기 중인 사항과 연결)과 원사업자·수급사업자의 규모에 따라 달라진다 ② 인쇄 문서의 조항 문구(일반적인 구성이며 입력한 내용만 채움, 하자담보·대금 조정·지연이자는 "관계 법령에 따른다"로 둠) ③ 건설산업기본법상 하도급 계약 내용(계약서 기재사항) 추가 반영 여부 — 이번에는 하도급법 기준만 반영.
