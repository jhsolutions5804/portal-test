# 프로젝트 변경·결정 이력 로그 + 메일 자동 정리 설계안 (r1 · 2026-10-16)

이 문서는 공개 저장소에 있으므로 **메일 내용·외부인 정보·원청 요청의 구체 내용·금액을 쓰지 않는다**(일반화한 설명만).

## 0. 목적
회의·미팅·메일에서 수시로 바뀌는 **변경·결정·요청**이 카톡방에만 흩어져 이력 관리가 안 되는 문제를 없앤다. 프로젝트별 이력으로 남겨 나중에 **찾고 근거로 쓰고**, **기한이 있는 요청을 놓치지 않게** 한다. 사람이 매일 옮겨 적을 여력이 없으므로 **자동 수집**이 핵심이다.

## 1. 결정 사항 (대표님 2026-10-16)
| # | 결정 |
|---|---|
| Q1 | 로그의 중심 = 회의·미팅·카톡·메일에서 나오는 변경·결정·요청의 이력. 일정·공정 변경은 시스템이 자동 기록 |
| Q2 | 분류 5개로 시작: ①발주처 요청·지시 ②일정 변경 ③범위·수량 변경 ④현장 이슈 ⑤회의 결정 |
| Q3 | 열람 = 해당 프로젝트 참여자 전체(기존 참여자 규칙 재사용) |
| Q4 | 알림 = 담당자에게만, 기한 D-2·당일 오전, 알림톡 + 화면 맨 위 표시 |
| Q5 | 담당자 지정 필수 아님. 새 기한 요청은 참여자 전체에 하루 1통 요약 → "내가 맡기" 1클릭 → 이후 그 사람에게만 알림 → D-1까지 미배정이면 팀장 개별 알림 |
| Q6 | 1단계 = 월간 보고서 반영 + 일정 자동 기록, 2단계 = "로그로 올리기". **견적·정산(단가) 연결은 하지 않음** |
| Q7 | 모바일 "+ 기록" 한 줄 입력, **사진 첨부 제외** |
| 우선순위 | 화면은 **기한 임박 요청 → 변경사항 → 전체 이력** 순 |

## 2. 원칙
- **로그에 단가·금액을 담지 않는다**(실무자 열람). 직접 입력은 금액 패턴 감지 시 경고, AI 요약은 금액 제거. 수량·사양·일정은 가능.
- **메일 본문·첨부는 저장하지 않는다**(요약 + 원문 링크만). 대용량 첨부는 열지 않는다.
- **"대외비"·금액이 든 메일은 존재만 기록**(상세는 관리자만).
- 개인 연락처·외부인 메일 주소는 저장하지 않는다.
- 원청 보안 규정 확인 전에는 AI 입력을 제목·요약 중심으로 최소화한다.
- 새 컬렉션은 **서버 함수 경유**로만 읽고 쓴다(참여자 규칙 서버 판정) + 규칙 시험.

## 3. 화면
- **프로젝트 화면 "이력" 탭**(참여자): ①기한 임박 요청(마감 임박순, 미회신 표시, "내가 맡기") ②변경사항(일정·수량·사양) ③전체 이력(분류·기간·출처 필터).
- **PJT 메인 홈 3단(대표님 2026-10-17 — 프로젝트를 고르기 전의 PJT 홈, 개별 프로젝트 홈 아님)**: 통합 일정 달력 | 선택한 날 일정 | **이력관리**. 이력관리 = **내가 볼 수 있는 모든 진행 중 프로젝트의 이력 요약**(기한 임박 최대 5건 + 최근 이력 최대 8건, 마감 임박순은 프로젝트를 가로질러) + 항목마다 프로젝트 칩(누르면 그 프로젝트 이력 탭) + 프로젝트 필터 + "＋ 기록"(**프로젝트를 골라야 제출**, 마지막 선택 기억). 서버 함수 pjtLogAct 의 `listAll`(프로젝트마다 참여자 판정, 못 보는 프로젝트는 존재도 알리지 않음, 종료 프로젝트 제외). 단 수는 브라우저 폭이 아니라 **홈이 실제로 차지하는 폭**(오른쪽 파일 서랍이 열리면 줄어듦)으로 정한다 — 넓으면 3단·보통이면 2단(이력관리는 아래 한 줄)·좁으면 1단. 개별 프로젝트 화면은 "이력" 탭(그 프로젝트만)을 쓴다. 두 곳이 같은 부품(`log-panel.js`)을 쓴다.
- **모바일(m/) "+ 기록"**: 프로젝트(마지막 사용 기본) · 분류 칩 5개 · 한 줄 요약 · 출처 칩(회의·카톡·전화·현장). 사진 없음.
- **확정**: 팀장·PJT 권한자가 후보(AI 초안)를 확정. 참여자는 열람·직접 입력.

## 4. 상태 흐름
`후보(AI)` → `확정` → `처리 중(누군가 맡음)` → `회신·조치 완료` → `종결`(또는 `보류`).
- 회신 감지: 프로젝트 메일의 보낸편지에서 같은 스레드에 회신이 생기면 "회신됨" 표시, **종결은 사람이 확인**.
- 변경사항은 회신 대신 **"영향 확인"** 체크(공정·월간 보고서 반영 여부).

## 5. 데이터 모델
`pjt_log/{pjtId}/entries/{id}`: `date`, `category`(5종), `title`(한 줄, 금액 없음), `source`(회의|카톡|전화|현장|메일|일정), `sourceRef`(원문 링크·일정 id), `dueDate?`, `status`, `claimedBy?`, `replyDetected`, `createdBy`, `confirmedBy?`, `createdAt`. **금액·단가 필드 없음.**
`mail_ingest/{messageHash}`(서버 전용): 처리 상태만(본문 없음).

## 6. 기록 방식
1. **자동(1단계)**: 일정 등록·변경·취소, 월간 보고서 인입, 메일 수집.
2. **직접 입력**: PC·모바일 한 줄.
3. **2단계**: 공사일보 비고·업무일지 이슈 → "로그로 올리기" 1클릭(중복 입력 방지).
4. **후순위·선택**: 카톡 "대화 내보내기" 텍스트 업로드 → AI 후보 → 사람 확인(카톡은 자동 연동 불가).
5. **브리티(원청 메신저)**: 연동 불가로 확인 — 중요한 지시는 메일 확정 공지·회의록으로 남기도록 요청하는 운영 방안을 별도 검토.

## 7. 메일 자동 수집 파이프라인
프로젝트용 Gmail → **필터로 회사 공용 사서함에 자동 전달**(권장) → 서버가 그 사서함만 Graph `Mail.Read`(특정 사서함 한정)로 읽음 → 전처리(대외비·금액 마스킹, 첨부 무시) → AI 분류(5분류·프로젝트·기한·요청/변경/회신 구분) → 스레드 병합·중복 제거 → 회신 감지 → 후보 생성 → 팀장 확정.
- 프로젝트 판별: 제목·본문의 프로젝트 이름 + 발신 부서(분류함 없음 → 사람 확인 병행).
- 시제품(제목·요약 기준)에서 기한 추출·변경 감지·스레드 연결·답변 대기 추적의 가치를 확인함.

## 7-1. 메일 프로젝트 분류 — 공용 사서함이 하나라서 생기는 문제 (대표님 2026-10-17 지적)
**문제**: 사서함이 하나이고 원청 메일은 프로젝트별 주소로 오지 않는다. 진행 중 프로젝트가 여럿(본섭 9개 중 진행 8개)이고 **이름이 서로 포함되는 쌍이 있어**(한 프로젝트 이름이 다른 프로젝트 이름의 앞부분) 이름만 보면 어느 쪽인지 갈린다. 지금까지 시제품은 기한 추출·변경 감지·스레드 연결·답변 대기 추적의 가치만 확인했고 **프로젝트 판별 정확도는 측정한 적이 없다**.
**원칙**: ① **모르면 찍지 않는다** — 확신이 낮으면 어느 프로젝트에도 넣지 않고 "미분류"로 둔다 ② 후보(AI 초안)는 확정 권한자만 보므로(구현됨) 잘못 분류돼도 다른 프로젝트 참여자에게 새지 않는다 ③ 미분류라도 **기한이 있는 요청은 관리 권한자에게 알려** 놓치지 않는다.
**분류 신호(위에서부터, 싸고 확실한 순)**: ⓐ 같은 스레드는 먼저 확정된 항목의 프로젝트를 그대로 ⓑ **발신자→프로젝트 학습**(권한자가 확정할 때마다 기억 — 한 담당자가 한두 프로젝트만 맡는 경우가 많음) ⓒ 프로젝트별 **별칭 목록**(프로젝트 설정에서 편집: 약칭·공종·동 이름) 일치, 더 긴 별칭 우선, 둘 이상이 맞으면 모호 → 사람에게 ⓓ AI 는 요약·기한·분류 5종과 프로젝트 **후보 1~2개 + 확신도** 제안만(자동 확정 아님).
**화면**: 전체 PJT 홈(프로젝트를 고르기 전)에 **"미분류 메일" 받은함**(관리 권한자만) — 한 건씩 프로젝트를 1클릭으로 지정하면 그 프로젝트 이력 후보로 들어가고, 발신자→프로젝트가 학습된다.
**운영 보조**: 우리가 회신할 때 제목에 프로젝트 약칭을 붙이면 이후 스레드 분류가 정확해진다(원청에도 제목 말머리를 부탁해 볼 수 있음).
**먼저 측정**: 실제 메일 약 100~200건에 정답(프로젝트)을 붙여 ⓐ~ⓓ 정확도를 잰 뒤 개발한다. 자동 제안이 맞는 비율이 충분하면 미분류 받은함은 예외 처리용, 낮으면 분류는 사람이 하고 AI 는 요약·기한 추출만 맡긴다(그것만으로도 가치가 있음). 측정 전에는 메일 수집(§10 순서 5)을 만들지 않는다.

## 7-2. Gmail 직접 수집 방식 검토 (대표님 2026-10-18: "Gmail 계정에서 자동으로 불러오도록 설계하자")
§7 의 기존안은 프로젝트용 Gmail → 자동 전달 → 회사 공용 사서함(M365) → 서버가 그 사서함만 읽는 구조였다. 대표님 요청은 **Gmail 을 서버가 직접 읽는 방식(A)** 이다. 서버에 메일을 읽는 코드는 아직 없어(메일 보내기 `mailer.js` 만 있음) 방식을 바꿔도 버릴 코드는 없다.
- **대상은 프로젝트용 Gmail 하나뿐.** 개인 업무 메일(정산·견적이 많음)은 연결하지 않는다(채널 구분은 대표님 확인).
- **접근 방식**: 서버 함수가 Gmail API 로 새 메일을 주기적으로 읽는다(읽기 전용 범위 `gmail.readonly` — 보내기·삭제·수정 불가). 로그인 토큰은 Secret Manager 에 둔다(기존 `defineSecret` 방식). 새 패키지(`googleapis`) 추가 필요.
- **가장 큰 위험 — 토큰 만료**: `gmail.readonly` 는 구글이 "제한된 범위"로 분류한다. 개인 Gmail 을 읽는 앱이 구글 클라우드에서 **\"테스트\" 상태면 로그인 토큰이 7일마다 만료**돼 일주일마다 대표님이 다시 승인해야 한다(자동 수집으로는 치명적). 앱을 \"게시(운영)\" 상태로 바꾸면 만료가 없어지는데, **제한 범위라 구글 심사가 필요한지는 자료마다 달라 확정하지 못했다**(본인 메일만 읽는 개인용은 심사 없이 넘어간다는 설명도 있음). → **착수 전에 구글 공식 문서·실제 화면으로 먼저 확인**한다. 확인 결과가 \"심사 필요\"이면 기존안(B, 자동 전달 + M365 공용 사서함)으로 되돌린다.
- **원칙은 그대로**(§2): 본문·첨부는 저장하지 않고 요약+원문 링크만, 대외비·금액 메일은 존재만 기록, 외부인 연락처 저장 안 함, 후보는 확정 권한자만 본다, 모르면 찍지 않는다(미분류), 원청 보안 규정 확인 전에는 AI 입력을 제목·발신 부서·요약 중심으로 최소화(설정값으로 범위를 바꿀 수 있게 만든다).
- **정확도 측정을 \"수작업 100~200건\" 대신 \"그림자 운영\"으로 대체하는 안**: 수집을 켜되 후보만 만들고(권한자만 열람), 권한자가 프로젝트를 확정·교정하는 기록으로 자동 분류의 정확도를 센다. 대표님이 한 번에 몇 시간을 쓰지 않아도 되고, 몇 주 쓰면 실제 정확도가 나온다. 대신 정확도가 나오기까지는 미분류 받은함을 사람이 비우는 부담이 있다.
- **결정 필요**: ①Gmail 직접(A) vs 전달+M365(B) — A 는 위 토큰 만료 확인 결과에 달림 ②정확도 측정을 수작업 vs 그림자 운영 ③어떤 메일을 가져올지(받은편지함 전체 / 라벨·발신 도메인 허용 목록) ④원청 보안 규정 확인 시점(AI 입력 범위)

- **계정 실사 결과(2026-10-18, 읽기 전용·보낸 사람/제목/분류 표시만 확인, 본문 미열람, 대표님 요청)**:
  - 프로젝트용 Gmail 은 **업무 전용 계정**이고 최근 받은편지함은 거의 전부 업무 메일(원청 공지·협력사 발신·회신)이다.
  - **광고는 사실상 없음**: Gmail 이 프로모션으로 분류한 것은 18통, 한 업체의 마케팅 메일이고 가장 최근이 2025-11.
  - **Google 설문 \"작성해 주셔서 감사합니다\" 접수 확인 메일**이 꾸준히 온다(현장 업무용 설문 양식을 제출한 영수증). 새 요청·기한 정보는 없다 → **결정(대표님 2026-10-18): 수집은 하되 이력 후보로는 올리지 않는다**(처리 완료 표시만).
  - **미확인(제목을 아직 보지 않음 — 확정 아님)**: Google 계정 보안 알림, 메일 반송 알림(`mailer-daemon`). 발신 주소만으로 분류하지 말고 제목을 확인한 뒤 정한다.
  - 우리 계정이 보낸 메일(보낸편지함)이 참조(CC)로 받은편지함에도 함께 보인다 → 수집 때 **발신자가 우리 계정인 메일은 따로 취급**(회신 감지 신호로 사용).
  - **대용량 첨부가 매우 많다**(수 MB~수십 MB) → \"대용량 첨부는 열지 않는다\"(§2)가 필수.
  - 원청 공지는 **여러 협력사에 동시 발송**(수신처 10~100곳 + 참조 다수)되고 같은 계정이 **여러 현장의 메일을 함께** 받는다 → 프로젝트 판별은 제목의 현장 구분 표기와 발신 부서 신호를 우선 활용(§7-1 ⓒ와 같은 방향).
  - 제목 앞머리에 **기한 표기**(예: \"~00/00 퇴근전\")가 붙는 요청이 흔하다 → 기한 추출 규칙의 첫 번째 후보.
- **토큰 만료 공식 확인(2026-10-18, 구글 공식 문서)**:
  - **확정**: 구글 클라우드 프로젝트가 **외부(External) 사용자 유형 + \"테스트\" 게시 상태**이면 refresh token 이 **7일 뒤 만료**된다(Google Ads·Google Health API 문서가 공통 OAuth 규칙으로 명시). 공식 해결책은 게시 상태를 **\"운영(In production)\"** 으로 바꾸는 것.
  - **공식 안내**(\"Manage App Audience\", support.google.com/cloud/answer/15549945): \"운영\" 게시 프로젝트가 Gmail 같은 민감·제한 범위를 요청하면 **심사(verification)를 마쳐야 하고**, 심사 전에는 \"확인되지 않은 앱\" 경고 화면이 뜨며 **새 사용자 100명 상한**이 있다.
  - **확정하지 못함**: 심사 없이 **대표님 본인 계정 1개만** 읽는 개인용으로 \"운영\" 게시해 경고 화면을 넘기며 계속 쓸 수 있는지, 그 경우 토큰이 끊기지 않는지는 공식 문서로 확인하지 못했다(업체 블로그는 \"제한 범위는 심사+연 1회 보안 평가가 필요, 우회 없음\"이라고 하나 다른 사람에게 서비스하는 앱을 전제로 한 글이고 공식 문서가 아님).
  - **설계 판단**: 방식 A(Gmail 직접)는 \"개인 앱을 심사 없이 운영 게시해 계속 쓸 수 있다\"가 **실제 시험으로 확인될 때만** 안전하다. 안 되면 일주일마다 재승인하거나 구글 심사(연 1회 보안 평가 포함)를 받아야 해 사내 포털 하나에는 과하다. 방식 B(자동 전달 + 회사 사서함)는 구글 OAuth 를 쓰지 않아 이 문제가 없다. **A 를 택하면 구글 클라우드에서 읽기 권한 앱을 만들어 운영 게시한 뒤 토큰이 7일을 넘겨 살아 있는지 일주일 지켜보는 시험을 첫 단계로 한다**(실패하면 B 로 전환).
- **방식 B 확정(2026-10-18, 대표님: "B로 하자")**: 프로젝트용 Gmail 의 **전체 수신 메일을 회사 Microsoft 365 공용 사서함으로 자동 전달** → 서버가 그 사서함만 Graph 로 읽는다(§7 기존안). 구글 OAuth(토큰 7일 만료·심사) 문제를 피한다. 가져올 범위는 "전부 전달 + 서버에서 거름"(설문 접수 확인 등은 처리 완료 표시만).
  - **재사용 결정(2026-10-18, 대표님)**: 새로 만들지 않고 **이미 있는 "PJT 일정" 공유 사서함을 메일 수집에도 쓴다**(포털 일정을 Outlook 공유 캘린더로 보내는 용도로 이전에 만든 것). 근거(Exchange 관리 센터에서 직접 확인, 읽기만): 공유 사서함, 사용량 **2.34MB / 49.5GB**(여유 큼), **읽기 및 관리(모든 액세스) 권한은 1명뿐·다른 사용자로 보내기 0명** → 직원 여러 명이 메일 폴더를 열 수 있는 상태가 아니다(직원은 달력만 공유 캘린더로 추가). 달력과 메일은 폴더가 달라 섞이지 않는다. **조건**: ⓐ수집용 Entra 앱은 **달력 연동 앱과 별도**로 만든다 ⓑ그 앱은 **이 사서함 하나만** 읽도록 Exchange 에서 제한(필수, 아래 ⑥) ⓒ모든 액세스 권한 1명이 누구인지는 확인하지 못했다(이름 확인은 권한을 바꾸는 편집 창을 열어야 해서 보류) ⓓ달력 공유 권한(누가 달력을 보는지)은 받은편지함 접근과 무관해 확인하지 않았다.
  - **재사용으로 바뀌는 선행 설정**: ①사서함 생성은 **생략**. ②수신 크기 한도 150MB 상향·③대표님 접근 권한(이미 있을 수 있음, 확인)·④Gmail 전달·⑤수집용 Entra 앱·⑥한 사서함 한정은 **그대로 필요**.
  - **Gmail 쪽 흔적(공식 도움말 확인)**: 자동 전달은 "새로 도착하는 메일의 사본을 보내는" 설정이고 스팸은 전달하지 않는다. Gmail 쪽 사본 처리(받은편지함 유지 등)를 고를 수 있고 **"받은편지함에 유지"가 권장**이다. 켠 뒤 1주일간 안내 메시지가 뜬다. **보낸편지함에 기록이 남는지는 공식 문서에 없다**(자동 전달은 남지 않는 것으로 알고 있으나 미확인 → 전달을 켠 뒤 보낸편지함에 새 항목이 안 생기는지 대표님이 한 번 확인). **전달이 실패하면 Gmail 받은편지함에 반송 알림이 생긴다**(큰 메일이 크기 한도에 걸릴 때) → 150MB 상향이 중요. **실제 확인(2026-10-18, 자동 전달)**: 켠 뒤 시험 메일이 약 9초 만에 사서함에 도착했고 **원래 발신자·수신자·제목이 그대로 유지**됐다. **Gmail 보낸편지함에는 새 항목이 생기지 않았다**(대표님 확인)로 위 "미확인"은 해소. 반대로 **수동 전달은 부적합**하다 — 발신자가 Gmail 계정으로 바뀌고 제목에 Fwd: 가 붙으며, 같은 대화에 메시지가 추가되면서 **원본이 읽음 처리**됐다(수동 전달은 수집 경로로 쓰지 않는다). 첨부(엑셀 2건)와 본문 이미지는 수동 전달에서도 함께 도착했다. 대용량(30MB급) 도착은 실제 큰 메일이 올 때 확인한다.
  - **선행 설정(대표님 몫, 순서대로)**: ① M365 관리센터에서 **공용 사서함 생성** ② **그 사서함의 수신 크기 한도를 150MB 로 상향**(Exchange Online 기본 수신 한도는 **36MB**, 최대 150MB — 이 계정에는 30MB급 메일이 있고 한도를 넘는 메일은 전달 단계에서 거절돼 서버가 존재를 모른다. 한도는 첨부가 아니라 **인코딩 포함 메시지 전체 크기**) ③ 공용 사서함에 대표님 계정의 접근 권한 부여(Gmail 이 보내는 **전달 확인 코드가 그 사서함으로 도착**하므로 열어 봐야 함) ④ Gmail 설정에서 전달 주소 추가·확인 코드 입력 후 **수신 메일 전달 켜기**(Gmail 사본은 남김) ⑤ 서버용 Entra 앱 등록 + `Mail.Read` **애플리케이션 권한** ⑥ **앱이 그 공용 사서함 하나만 읽도록 Exchange 쪽에서 제한**.
  - **⑥은 필수 보안 설정이다**: Entra 의 `Mail.Read` 애플리케이션 권한은 **기본값이 "테넌트 안의 모든 사서함"** 이다(마이크로소프트 공식 문서). 제한하지 않으면 이 수집 앱이 회사 전체 메일함을 읽을 수 있다. 제한 방법은 Exchange PowerShell 의 `New-ApplicationAccessPolicy` 를 공식 문서가 안내하나, 마이크로소프트는 이를 구형(legacy)으로 보고 **Exchange RBAC for Applications** 로 옮기라고 안내한다는 자료가 여럿이다 → **지금 어느 방식을 쓸지는 설정 착수 때 공식 문서로 다시 확인**하고, 설정 뒤 **다른 사서함을 읽으면 403 이 나오는지 시험**한다. 기존에 연결된 SharePoint 파일 패널용 Entra 앱과는 **별도 앱**으로 만든다(권한 범위 분리).
  - **알려진 한계 — 보낸 메일은 전달되지 않는다**: 자동 전달은 **들어오는 메일만** 옮긴다. 우리가 원청에 한 회신은 대표님 계정을 **참조(CC)로 넣었을 때만** 받은편지함에 보이므로, §4 의 "같은 스레드에 회신이 생기면 회신됨 표시"를 서버가 자동으로 못 하는 경우가 생긴다. 대안: ⓐ회신할 때 프로젝트 Gmail 을 참조에 넣는 습관(운영 안내) ⓑ이력 화면에서 사람이 "회신함" 1클릭 ⓒ원청이 다시 회신해 오는 메일의 인용 구조로 추정(정확도 낮음). **초기에는 ⓑ 를 기본으로 한다.**
  - **전달 시험 항목**: 30MB급 대용량 메일이 실제로 공용 사서함에 도착하는지, 원래 보낸 사람·제목·날짜·스레드 연결 정보가 유지되는지.

## 8. 알림
- 새 기한 요청: 참여자 전체에 **하루 1통 요약**.
- "내가 맡기" 이후: 그 사람에게만 D-2·당일 오전.
- D-1까지 미배정: 팀장 개별 알림.
- 채널: 알림톡(솔라피 연동·템플릿 심사 선행) — **1단계 출시는 화면 표시 먼저**, 알림은 연동 후. 전자결재 알림 방침("내 차례에만")과 **별도 방침**(담당이 정해지지 않은 요청이므로).

## 9. 권한
열람 = 프로젝트 참여자 전체(지정 없으면 PJT 권한자 전체, 관리자 항상, 종료 프로젝트는 관리자만). 입력 = 참여자. 확정 = 팀장·PJT 권한자. 금액·대외비 상세 = 관리자만.

## 10. 개발 순서
1. 데이터 모델·관리자/참여자 판정 서버 함수·규칙 + 시험 → 2. 로그 화면(PC·모바일) 직접 입력·필터 → 3. 일정 자동 기록 → 4. 월간 보고서 현장 층 인입(월간 보고서 설계와 함께) → 5. 메일 수집(전달 설정 선행) → 6. 알림(알림톡 연동 후) → 7. 2단계 "로그로 올리기".
각 단계 시험·테섭 배포(자동)·대표님 확인. 본섭은 새 컬렉션 규칙 게시(규칙 파이프라인) + 화면 배포.

## 11. 선행 과제 · 대표님 몫
- 회사 **공용 사서함 생성**(M365 관리), **수신 크기 한도 150MB 상향**, 프로젝트 Gmail **자동 전달 설정**(전달 확인 코드는 공용 사서함으로 도착), 서버용 Entra 앱 + **한 사서함 한정 제한**(§7-2 순서 ①~⑥).
- **원청 보안 규정 확인**(AI 처리 범위) — 확인 전에는 요약 중심.
- 알림톡: 솔라피 가입·충전·키 등록, 템플릿 심사.
